Error page

When a whole page cannot be shown, The Debate App replaces it with an icon, a plain heading, one sentence and a way back to somewhere useful. Nobody should feel they broke something.

Overview

Use an error page when the route itself fails. There are exactly four. When only one section of a page fails, keep the page and use an error empty state in that section instead.

  • Page not found: a link is old, or the meeting was deleted.
  • Sign in to continue: a protected endpoint answered 401 or the session ended (tokens last 120 minutes). After signing in the person returns to the page they asked for.
  • Something went wrong: the server failed. Retry or go back to meetings.
  • Offline: no connection on the first request; later drops use the persistent banner.

The page keeps the normal top bar, so navigation still works. The sign-in page is the exception: nobody is signed in, so there is no top bar.

Anatomy

  1. Icon.empty__icon (--size-avatar-xl) holding an .icon--lg line icon; decorative.
  2. HeadingThe page's <h1 class="empty__title">.
  3. Explanation.empty__text: what probably happened, in one sentence.
  4. Way back.empty__actions: Back to meetings, plus Try again or Sign in where it helps.

Variants

Four pages, one layout. The examples use <h2>; in the product the heading is the page's <h1>.

Sizes

One size: the page-scale empty state with an extra 64px above it so the message sits in the upper middle of the screen.

Responsive behaviour

  • Centred in main at every width; the text stops at 36ch.
  • On phones the two actions wrap onto two centred rows under the top bar.
  • The icon circle keeps its size on all screens.

Theming

Reads the same tokens as the empty state plus --color-accent-subtle for the icon circle (--color-danger-bg on the server error page). The heading uses --text-h3 from .empty__title. Nothing is theme specific.

Accessibility

Role and pattern

A normal page: skip link, top bar, main with one <h1>. The document <title> names the problem ("Page not found · The Debate App") so it is announced on load. The server should answer with the matching HTTP status (404, 401, 500).

Keyboard

KeyAction
TabSkip link, top bar, then the page actions in order.
Enter, SpaceRuns Try again; follows the links.

Focus

On a client-side route change to an error page, focus moves to the <h1> (with tabindex="-1") so the heading is read first.

Labelling

The icon is aria-hidden. The heading carries the whole message in words.

Motion

Touch

Actions are buttons at least 40px high, 12px apart, in the middle of the screen.

Content

  • Headings are plain: "We can’t find that page", "Sign in to continue", "Something went wrong on our side", "You’re offline".
  • Say what probably happened in one sentence and, where true, that the fix is waiting: "Meetings will load again when the connection is back."
  • The way back is a named place: "Back to meetings". The sign-in page needs "Sign in" instead.
  • Use typographic apostrophes in headings (can’t, You’re).
  • Avoid status codes and stack traces as headings or body copy.

Code

<main id="main" class="container">
  <div class="empty empty--error" style="padding-top: var(--space-16);">
    <span class="empty__icon"><svg class="icon icon--lg" aria-hidden="true">…</svg></span>
    <h1 class="empty__title" tabindex="-1">Something went wrong on our side</h1>
    <p class="empty__text">Try again in a moment. If it keeps happening, tell Jordan.</p>
    <div class="empty__actions">
      <button class="btn btn--primary" type="button">…Try again</button>
      <a class="btn" href="/meetings">Back to meetings</a>
    </div>
  </div>
</main>
