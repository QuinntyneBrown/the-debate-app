Form field

The field wraps one control with a visible label and, when the value is wrong, an error message that says how to fix it. There is no help text and no optional marker.

WCAG 2.2 AAStatus: stableNative <label>

Overview

Every text field, date input and time input sits inside a .field. The field stacks its parts in a fixed order: label, control, error. It has no look of its own beyond spacing and type.

  • Label (.field__label) is always visible and is a short noun: "Name", "Date", "Start", "End", "Username", "Password".
  • No help text and no optional marker. The product stance is no help unless a rule exists, and the mocks use neither .field__help nor .optional. Both classes still exist in ui.css; do not use them without a requirement.
  • Error (.field__error) is added below the control when the value is wrong, and says how to fix it: "Enter a name.", "End must be after start."

The rich-text editors on the meeting form (abstract, agenda, minutes) are labelled the same way; see form layout and rich-text editor.

Anatomy

  1. Label<label class="field__label" for>, --text-label, always visible.
  2. ControlAn .input or .textarea.
  3. Error (when invalid).field__error in --color-danger-fg with a ⚠ glyph, so colour is not the only cue.

Variants

One component; the parts you include make the variant.

End must be after start.
Label only (text, date, credentials); label with an error.
HTML
<div class="field">
  <label class="field__label" for="end">End</label>
  <input class="input" id="end" name="end" type="time" aria-invalid="true"
         aria-describedby="end-error">
  <div class="field__error" id="end-error">End must be after start.</div>
</div>

Sizes

The field takes its control's size; label and error text do not scale.

States

The field's state is its control's state, plus the error text when invalid. Focus and hover are forced on the control with data-state.

Both themes

End must be after start.
  • Errors appear after a submit attempt, never while typing; they clear when the field is next changed.
  • An invalid field keeps the value that was typed, so a typo can be fixed rather than retyped.

Responsive behaviour

  • The field is full width of its container on phones. Date and time inputs are capped (12rem and 10rem) so the box hints at the length of the answer; the meeting name takes the full width.
  • Label and error wrap freely; nothing truncates.
  • Fields stack in a single column, including Date, Start and End on the meeting form.

Theming

The field reads --color-fg-default (label) and --color-danger-fg (error). Both are re-mapped by the dark theme; the field itself has no component tokens. The gap between parts is --space-1.

Accessibility

Role and pattern

Native <label for> tied to the control's id. The error is tied with aria-describedby: aria-describedby="end-error". An invalid control sets aria-invalid="true".

Keyboard

KeyAction
Tab / Shift+TabMoves between controls; label and error are not focusable.
Error-summary linkMoves focus straight to the field; see form layout.

Focus

Focus is shown on the control, not the field. Clicking or tapping the label also focuses the control.

Labelling

Every control has a visible label (WCAG 3.3.2). The Debate App uses no placeholders, so nothing disappears when typing starts.

Contrast

Error on card

Motion

None. Errors appear without animation.

Touch

The label is part of the target: tapping it focuses the control, which helps on narrow time and date fields.

Content

  • Labels are short nouns in sentence case: "Name", "Date", "Start", "End", "Username", "Password".
  • Errors say how to fix it, not what went wrong in system terms: "Enter a name.", "End must be after start." Never "Invalid value".
  • Errors are one short sentence with a full stop, and do not blame the person.
  • No help text and no "(optional)" marker unless a requirement needs one.
