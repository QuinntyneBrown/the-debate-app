Skeleton

Grey shapes in the layout of the page that is coming, with a soft shimmer. They show where things will be, so the page does not jump when the data arrives.

WCAG 2.2 AAStatus: stablearia-busy on the container

Overview

Use skeletons for the first load of a page or section whose layout is known: the meeting list, one meeting, the edit form. Keep the real page chrome (top bar, page title, buttons that work without data) and swap only the data for skeletons.

  • For an action in progress, use a loading button or an inline status, not a skeleton.
  • If loading fails, replace the skeletons with an error error page or empty state.

Anatomy

  1. Date block.skeleton--rect at 3.5rem square: the size of the meeting's date tile, with a medium radius.
  2. Title bar.skeleton--title: 1.5em tall; the meeting row sets it to 60% wide.
  3. Text lines.skeleton--text: 1em tall; the row sets 35% for the time and 80% for the excerpt.
  4. Busy containerThe real list with aria-busy="true" and an aria-label that says what is loading.

Variants

Pick the shape that matches what will replace it.

Title, text lines, a field-height block (a text field), a square tile (a meeting date).
HTML
<span class="skeleton skeleton--title" aria-hidden="true"></span>
<span class="skeleton skeleton--text" aria-hidden="true"></span>
<span class="skeleton skeleton--rect" style="height: var(--control-height-md);" aria-hidden="true"></span>
<span class="skeleton skeleton--rect" style="width: 3.5rem; height: 3.5rem;" aria-hidden="true"></span>

Sizes

Text and title skeletons are sized in em, so they follow the font size of where they sit. Blocks take a height that matches the real content: --control-height-md for a text field, 3.5rem square for the meeting date tile.

States

A skeleton has one state, loading. The container moves from loading to loaded (or to an error).

Both themes

  • Loaded: remove aria-busy and the aria-label, and swap skeletons for content in one paint, so screen readers read the finished section once.
  • Failed: replace the whole section with an error empty state ("We couldn’t load your meetings").

Responsive behaviour

  • Skeletons live inside the real layout (grid, cards, hero), so they reflow exactly as the content will.
  • Show the number of placeholders that fills the first screen: three meeting rows on the list, not the whole history. Do not draw every meeting.
  • Fixed widths (a subtitle line of 10–14rem and a field block of 18rem in the mocks) must stay below 320px wide so they do not overflow a phone.

Theming

The shimmer is a gradient between --color-bg-subtle and --color-bg-subtle-hover, both tuned per theme, so skeletons are quiet grey on light cards and a lifted grey on dark ones.

Accessibility

Role and pattern

Every skeleton is aria-hidden="true". The section that is loading carries aria-busy="true" and an aria-label ("Loading meetings", "Loading meeting"), so assistive tech knows it is not ready and does not read half a page.

Keyboard

KeyAction
TabSkips skeletons. Real controls in the chrome (New meeting, the nav links) stay reachable while the data loads.

Focus

Skeletons never take focus. When content arrives, focus stays where it was.

Labelling

The busy container says what is loading in words. Keep the page <h1> real ("Meetings", "Edit meeting") so the page is identified from the start.

Contrast

Skeletons are decorative placeholders and are exempt from 1.4.11. The real text that replaces them uses the normal pairs:

Loaded text on card
Loaded meta on card

Motion

The shimmer runs once per --duration-loop (1.4 s). Under prefers-reduced-motion the animation is removed and the skeleton is a flat grey shape.

Touch

No targets.

Content

  • The busy label is "Loading" plus the thing: "Loading meetings", "Loading meeting".
  • Never put text inside a skeleton or show "Loading…" over it; the shapes are the message.
