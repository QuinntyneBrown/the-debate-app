Inline message

One line of text right next to the thing it is about. A field error tells someone how to fix one answer; the save status says whether the meeting is saving, saved or has unsaved changes.

WCAG 2.2 AAStatus: stablearia-describedby / role="status"

Overview

  • Field error (.field__error): under one input after a submit finds a problem with it. Pair it with the danger form summary ("Fix 2 things to save") when a form has more than one problem.
  • Inline status (.inline-status): the live status in the save bar beside the Save button: "Unsaved changes", "Saving…", then "Saved just now". Use a toast instead when the save takes the person somewhere else, such as after creating a meeting.

Do not use either for news that is not about the element beside it; that is an alert or a toast.

Anatomy

  1. Error glyph⚠ from .field__error::before; the text, not the glyph, carries the message.
  2. Error textSmall body text in --color-danger-fg, linked to the field with aria-describedby.
  3. Status dot.dot, 8px, currentColor; .dot--pulse while saving. Decorative.
  4. Status text"Unsaved changes" and "Saving…" muted; "✓ Saved just now" in success colour.

Both use small body text (--text-body-sm) at every size of field.

  • Field error appears after submit, never while typing; it clears once the field is valid on the next submit.
  • Saving… shows the pulsing dot until the server answers; then Saved just now replaces it in the same element, so it is announced once.

Responsive behaviour

  • Field errors wrap under the field at every width; the glyph stays on the first line.
  • The inline status sits beside the Save button in the save bar and wraps above it on a narrow screen.

Theming

Field errors read --color-danger-fg; inline status reads --color-fg-muted, or --color-success-fg with --success. The dot is currentColor, so it always matches the text. All three are tuned per theme to stay above 4.5:1 on cards, the page and dialogs.

Accessibility

Role and pattern

A field error is plain text tied to its control with aria-describedby, with aria-invalid="true" on the control (WCAG 3.3.1). An inline status is a role="status" live region that exists before the save starts, so the change of text is announced politely.

Keyboard

KeyAction
TabMessages are not stops. Focusing an invalid field reads its label, then its error.

Focus

On a failed submit focus moves to the form summary ("Fix 2 things to save"), or to the only invalid field when there is just one. The inline status never takes focus.

Labelling

Reference the error id in aria-describedby so the problem is read after the label. The ⚠ comes from CSS content and some screen readers read it as "warning sign"; the sentence still makes sense with it. Wrap the ✓ in "Saved" in aria-hidden so it is not read as "check mark".

Motion

The dot pulses once per --duration-loop (1.4 s). Under reduced motion it runs one cycle and stops; the word "Saving…" still says what is happening.

Touch

No targets.

Content

  • Errors say how to fix it, not what is wrong in the abstract: "Enter a name.", "End must be after start."
  • Keep it to one short sentence with a full stop; never blame the person.
  • Status: "Unsaved changes", "Saving…" (with the ellipsis character), then "Saved just now".
