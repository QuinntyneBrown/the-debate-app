Forms

Every form in the Debate App is a labelled field header followed by rich-text sections, checked when it is sent, with one primary button in the save bar.

Overview

The Debate App has three forms: sign in, create a meeting and edit a meeting. Create and edit share one layout, so an organiser learns it once. A meeting is a short header of fields (name, date, start, end) followed by a tab strip of three rich-text editors (abstract, agenda, minutes).

  • Labels sit above fields, always visible, never inside the field as placeholder text.
  • Short fields share a header. .meeting-form__header lays name, date, start and end out in one block; long content gets its own tab so the form never becomes a long scroll.
  • Only the primary action is filled. Save (or Create meeting) sits in the page header beside the save status; Delete lives in a separate .danger-zone below the form.
  • Checked when sent. Nothing is validated while typing; errors appear on submit with a linked summary and the first problem field is focused.

When to use

Use a form to collect or change information that is saved together. Use a dialog for a one-question decision ("Delete this meeting?") and an inline control for an instant toggle. Do not build a multi-step wizard: a meeting has seven fields and fits on one page.

Structure

Every form follows the same top-to-bottom order. The save bar is in the page header, outside the <form>, and points back to it with the form attribute.

Page header with title and save bar, then the field header. The tab strip of editors follows (see Tab strip and Rich-text editor).
  1. Back link ("Meetings") above the title.
  2. Page header: h1 ("New meeting" or "Edit meeting") and the .save-bar.
  3. Error summary, only after a failed submit.
  4. Field header: name, date, start, end.
  5. Tab strip with one rich-text editor per section: abstract, agenda, minutes.
  6. Danger zone (edit only): "Delete this meeting" with the Delete meeting button.

Components: Form layout, Form field, Text field, Save bar, Tab strip, Rich-text editor, Button.

Responsive

  • At 360px the header fields stack to one column; from 768px name takes a full row and date, start and end share the next.
  • The save bar wraps below the title on phones; the status text stays next to the button.
  • The editor toolbar wraps and the tab strip scrolls sideways rather than truncating tab names.

Accessibility

  • Every control has a visible <label> tied by for/id (3.3.2).
  • Errors use aria-invalid="true" and aria-describedby to the error text; the summary has role="alert", receives focus and links to each field (3.3.1, 3.3.3).
  • Date and time use native type="date" and type="time" inputs, so pickers and keyboard entry come from the platform.
  • The save status is a role="status" live region; busy state sets aria-busy="true" on the button.
  • Leaving the editor with unsaved changes opens the "Leave without saving?" dialog (3.3.4); see Dialogs and overlays.
  • The rich-text toolbar is a role="toolbar" with aria-pressed on toggle buttons and an aria-label on every icon button.

Content

  • Field labels are single nouns: Name, Date, Start, End, Abstract, Agenda, Minutes.
  • Field errors say what to do: "Enter a name." and "End must be after start."
  • The summary title counts the problems: "Fix 2 things to save".
  • Buttons: "Save" when editing, "Create meeting" when creating, "Sign in" on the sign-in form.
