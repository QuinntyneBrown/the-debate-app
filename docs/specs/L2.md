# L2 - Detailed Requirements

Every criterion below is traceable to a specific file in the implementation. Where the code's behavior is a consequence of a missing guard (for example, a null dereference), the criterion states the observable result and is marked *(observed)*.

Acceptance tests must carry a trace comment header, e.g. `// Traces to: L2-001, L2-002`.

---

## L2-001: Meeting add-or-update endpoint
**Traces to:** L1-001

`POST api/meeting/add` and `PUT api/meeting/update` both call the same add-or-update logic (`MeetingService.AddOrUpdate`). The request body is a `MeetingDto` (`id`, `date`, `start`, `end`, `abstract`, `agenda`, `minutes`, `name`). Both endpoints are anonymous because `MeetingController` has no `[Authorize]` attribute.

**Acceptance Criteria:**
1. Given no non-deleted meeting exists with the request `id`, when the request is posted, then a new meeting is created with the request's `name`, `abstract`, `agenda`, `minutes`, `start`, and `end`, and the response is HTTP 200 with the new meeting's `id` and fields.
2. Given a non-deleted meeting exists with the request `id`, when the request is posted, then that meeting's `name`, `abstract`, `agenda`, `minutes`, `start`, and `end` are overwritten with the request values.
3. Given the request `date` is a non-empty string, when the request is posted, then `date` is parsed with `DateTime.Parse` and stored on the meeting.
4. Given the request `date` is null or empty, when the request is posted, then the stored `date` is left unchanged.
5. Given a meeting with the request `id` exists but is soft-deleted, when the request is posted, then a new meeting is created rather than the deleted one being revived.
6. Given no `Authorization` header, when `POST api/meeting/add` is called, then the request is not rejected for lack of authentication.

## L2-002: Meeting list endpoint
**Traces to:** L1-001

`GET api/meeting/get` is anonymous and returns all non-deleted meetings.

**Acceptance Criteria:**
1. Given meetings exist, when `GET api/meeting/get` is called without credentials, then HTTP 200 is returned with a JSON array of `MeetingDto` objects for every meeting whose `isDeleted` is false.
2. Given a meeting is soft-deleted, when the list is requested, then that meeting is absent from the array.
3. Given a meeting has a `date`, when it is returned, then `date` is a string formatted `yyyy-MM-dd`.
4. Given a meeting has a null `date`, when it is returned, then `date` is an empty string *(observed: `string.Format("{0:yyyy-MM-dd}", null)`)*.

## L2-003: Meeting get-by-id endpoint
**Traces to:** L1-001

`GET api/meeting/getById?id={id}` returns a single non-deleted meeting. The action has no `[AllowAnonymous]`, but because the controller has no `[Authorize]`, it is anonymous.

**Acceptance Criteria:**
1. Given a non-deleted meeting with the given `id` exists, when the endpoint is called, then HTTP 200 is returned with that meeting's `MeetingDto`.
2. Given no non-deleted meeting with the given `id` exists, when the endpoint is called, then the request fails with a server error *(observed: `new MeetingDto(null)` dereferences null)*.

## L2-004: Meeting remove endpoint
**Traces to:** L1-001, L1-007

`DELETE api/meeting/remove?id={id}` soft-deletes a meeting.

**Acceptance Criteria:**
1. Given a meeting with the given `id` exists, when the endpoint is called, then the meeting's `IsDeleted` is set to true, changes are saved, and HTTP 200 is returned with the integer `id` as the body.
2. Given no meeting with the given `id` exists, when the endpoint is called, then the request fails with a server error *(observed: `GetById` returns null and `IsDeleted` is assigned on null)*.

## L2-005: Article endpoints
**Traces to:** L1-002

`ArticleController` is `[Authorize]`d with routes `add` (POST), `update` (PUT), `get` (GET, anonymous), `getById` (GET), `remove` (DELETE). The DTO exposes only `id` and `title`.

**Acceptance Criteria:**
1. Given a valid bearer token, when `POST api/article/add` is sent with `{ id: 0, title }`, then a new article is created with that `title` and HTTP 200 returns `{ id, title }`.
2. Given a valid bearer token and a non-deleted article with the request `id`, when `PUT api/article/update` is sent, then that article's `title` is overwritten.
3. Given no credentials, when `GET api/article/get` is called, then HTTP 200 returns all non-deleted articles as `{ id, title }`.
4. Given no credentials, when `GET api/article/getById`, `POST api/article/add`, `PUT api/article/update`, or `DELETE api/article/remove` is called, then HTTP 401 is returned.
5. Given a valid bearer token, when `DELETE api/article/remove?id={id}` is called for an existing article, then `IsDeleted` is set true and HTTP 200 returns the `id`.
6. Given an article is soft-deleted, when `getById` or `get` is called, then it is not returned.

**Traces to:** L1-005

5. Given a valid bearer token, when `DELETE api/digitalasset/remove?id={id}` is called for an existing record, then `IsDeleted` is set true and HTTP 200 returns the `id`.

## L2-011: Digital asset upload
**Traces to:** L1-005

`POST api/digitalasset/upload` is anonymous and accepts `multipart/form-data`. Every file part is read fully into memory and stored as a `DigitalAsset` row.

**Acceptance Criteria:**
1. Given a `multipart/form-data` request with one or more file parts, when it is posted, then for each file a `DigitalAsset` is saved with `FileName` equal to the part's file name (surrounding quotes stripped, `&` replaced with `and`, directory portion removed), `Bytes` equal to the file content, and `ContentType` equal to the part's `Content-Type` header.
2. Given the upload succeeds, when the response is returned, then it is HTTP 200 with `{ files: [ { id, name }, ... ] }` containing one entry per stored file in upload order.
3. Given the request is not `multipart/form-data`, when it is posted, then HTTP 200 is returned with `{ files: [] }` *(observed: the `BadRequest` exception is caught and swallowed)*.
4. Given a multipart part lacks a `Content-Disposition` header, when it is posted, then HTTP 200 is returned with `{ files: [] }` and nothing is saved *(observed: `InvalidOperationException` is swallowed)*.
5. Given a multipart request contains non-file form fields, when it is posted, then those fields are read into form data and are not stored as assets.
6. Given no `Authorization` header, when the upload is posted, then it is accepted.

## L2-012: Digital asset serve
**Traces to:** L1-005

`GET api/digitalasset/serve?uniqueId={guid}` or `?name={name}` is anonymous, cached, and returns raw bytes.

**Acceptance Criteria:**
1. Given a `uniqueId` query parameter matching an asset, when the endpoint is called, then HTTP 200 is returned with the asset's `Bytes` as the body and `Content-Type` equal to the stored `ContentType`.
2. Given no `uniqueId` and a `name` query parameter matching an asset's `Name`, when the endpoint is called, then the same response as criterion 1 is returned for the first matching asset.
3. Given neither parameter matches an asset, when the endpoint is called, then HTTP 200 is returned with no content.
4. Given the same `uniqueId` (or `name`) is requested twice, when the second request arrives, then the asset is served from the in-memory cache keyed by the `uniqueId` string (or `name`) without re-querying the database, and HTTP cache headers advertise a client and server lifetime of 1000 seconds.
5. Given a soft-deleted asset, when it is requested by `uniqueId` or `name`, then it is still served *(observed: the lookup does not filter on `IsDeleted`)*.

## L2-013: Token endpoint (resource owner password grant)
**Traces to:** L1-006

The OAuth2 token endpoint path, expiry, key, issuer, audience, and authentication type come from the `authConfiguration` section in `App.config`: `tokenPath="/api/user/token"`, `expirationMinutes="120"`, `jwtIssuer="localhost"`, `jwtAudience="all"`, `authType="olivia"`. Insecure HTTP is allowed.

**Acceptance Criteria:**
1. Given a `POST /api/user/token` with `Content-Type: application/x-www-form-urlencoded` and body `grant_type=password&username={u}&password={p}`, when `{u}` matches a non-deleted user's `Username` case-insensitively and the SHA-256/Base64 transform of `{p}` equals the stored `Password` for a user whose `Username` matches exactly, then HTTP 200 is returned with an `access_token` that is a JWT, plus `token_type` and `expires_in`.
2. Given the username does not match any non-deleted user (case-insensitive), when the token is requested, then the response is an OAuth error with description `Invalid credentials`.
3. Given the username matches but the transformed password does not, when the token is requested, then the response is an OAuth error with description `Invalid credentials`.
4. Given credential validation throws, when the token is requested, then the response is an OAuth error whose description is the exception message.
5. Given a token is issued, when it is decoded, then `iss` is `localhost`, `aud` is `all`, `exp` is 120 minutes after issuance, and it is signed with HMAC-SHA256 using the Base64-decoded `jwtKey`.
6. Given a token is issued, when its claims are inspected, then it contains one `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/name` claim equal to the submitted username and one `http://schemas.microsoft.com/ws/2008/06/identity/claims/role` claim per role name attached to the user.
7. Given the token request arrives over plain HTTP, when it is processed, then it is not rejected for being insecure.
8. Given a user's claims have been loaded once, when a second token is requested for the same username, then the user and roles are read from the in-memory cache under key `User: {username}` rather than the database.

## L2-014: Bearer token validation on protected endpoints
**Traces to:** L1-006

JWT bearer authentication is configured with the configured issuer, audience, and symmetric key. The host principal is suppressed and the OAuth bearer authentication filter is the only authentication source.

**Acceptance Criteria:**
1. Given a protected endpoint (any action without `[AllowAnonymous]` on a controller with `[Authorize]`), when a request carries `Authorization: Bearer {valid token}`, then the request is authorized and `User.Identity.Name` equals the token's name claim.
2. Given a protected endpoint, when the request has no `Authorization` header, then HTTP 401 is returned.
3. Given a protected endpoint, when the bearer token is expired, has the wrong audience, wrong issuer, or an invalid signature, then HTTP 401 is returned.
4. Given the application starts, when `authConfiguration` is missing from configuration, then startup fails with a `ConfigurationErrorsException` naming `authConfiguration`.

## L2-015: Password transform
**Traces to:** L1-006

`EncryptionService.TransformPassword` is the only password transform used for both seeding and validation.

**Acceptance Criteria:**
1. Given a plaintext password, when it is transformed, then the result is the Base64 encoding of the SHA-256 hash of the UTF-8 bytes of the password, with no salt.
2. Given the same password transformed twice, when the results are compared, then they are identical.

## L2-016: Soft-delete semantics
**Traces to:** L1-007

All services for Meeting, Article, Architecture, ArchitectureItem, User, DigitalAsset, Role, and InvitationCode share the same pattern.

**Acceptance Criteria:**
1. Given any entity is removed through its `remove` action, when the database row is inspected, then the row still exists with `IsDeleted = true`.
2. Given an entity has `IsDeleted = true`, when `get` or `getById` is called, then it is excluded.
3. Given an entity has `IsDeleted = true`, when an add-or-update request arrives with its `id`, then a new entity is inserted instead of updating the deleted one.
4. Given `EFRepository.GetById`, when it is called with an unknown id, then it returns null.

## L2-024: Meeting create and edit (client)

## L2-028: Tab strip custom element
**Traces to:** L1-013

`ce-fancy-tabs` is a shadow-DOM tab strip with `title`-slotted tabs and default-slotted panels.

**Acceptance Criteria:**
1. Given children with `slot="title"` and panel elements, when connected, then the host has `role="tablist"`, each tab has `role="tab"`, and each panel has `role="tabpanel"` and `tabindex="0"`.

5. Given focus is in the tab slot, when ArrowLeft or ArrowUp is pressed, then the previous tab is selected (wrapping from first to last); when ArrowRight or ArrowDown is pressed, then the next tab is selected (wrapping from last to first).

## L2-029: Drop zone custom element
**Traces to:** L1-013

`ce-drop-zone` is a shadow-DOM file drop target.

**Acceptance Criteria:**
1. Given `ce-drop-zone` renders, when inspected, then it shows an anchor whose text is the `caption` attribute or `Drop Zone` when no caption is set.
